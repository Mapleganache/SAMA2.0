# SAMA 2.0 磨床维修多智能体说明

这份说明对应 `electron/services/sama2.0` 里现在正在跑的代码。系统只处理磨床维修问题：先判断问题是简单还是复杂；简单问题由主智能体直接回答；复杂故障由五个角色各写一套方案，再由评判智能体按固定权重选出一套。

## 1. 总流程

用户提交一段故障描述后，Main Agent 做三件事：抽出现象和设备、判断复杂度、决定走哪条路。

简单问题到此结束。Main 先查一次本地资料和测点模板，再写一段直接答复，五个 Sub 和 Judge 都不会启动。

复杂问题不拆题。五个 Sub 拿到的是同一段完整描述，彼此看不到对方的记录，各自在自己的轮次里思考、调用工具、写出一套方案。全部结束后，Judge 只打分，不重写方案。加权分由程序计算，最高分的那一套作为给用户的维修方案，并附上评分和其他方案的不足。

作者可以打开「强制走五路方案」。这时跳过复杂度判断，名词解释也会进入五路。这是调试开关，默认关闭。

## 2. Main Agent

Main 不负责把问题切成五个子题。它的任务是受理、分类和路由。

它从原文里提取四类信息，供后面的评判注意事项使用：

- 现象：发热、振动、异响、精度或表面、运动异常、液压润滑、报警
- 设备：是否能认出外圆磨、内圆磨、无心磨、平面磨，或 STUDER、高桥、MIKROSA 等名称
- 现场约束：例如不能随意停机、没有量具、不许拆卸
- 相关子系统：主轴、砂轮、头架尾架、导轮、液压润滑、冷却、进给、工作台

### 2.1 复杂度判断

判断分两段。硬规则先执行，这一步不调用模型。硬规则给不出结论时，才调用分类模型。复杂信号优先于简单信号，避免把多现象故障放成简单题。

直接判为复杂，满足任意一条即可：

- 同时出现至少两类现象，例如发热加上振动、异响、精度、运动、泄漏或报警
- 故障是偶发、间歇、时有时无
- 已经排查、更换或处理后问题还在
- 故障需要结合型号、工况或历史维修记录一起判断

直接判为简单，且上面的复杂条件都不成立：

- 名词或概念解释，例如「什么是磨床静压轴承」
- 参数、保养周期、润滑油品、备件型号查询
- 很短的日常保养问题，例如「导轨怎么日常保养」

像「主轴发热」这种只有单一现象、又没有偶发或复查信息的句子，硬规则不判。分类模型只输出一个 JSON：`level` 为 `simple` 或 `complex`，外加一句理由。分类模型失败时，按复杂问题处理，避免漏掉需要排查的故障。没有 API Key 时不会偷偷降级，直接提示去配置密钥。

### 2.2 简单问题怎么回答

Main 调用两个工具：`search_knowledge` 和 `lookup_baseline`。然后用一次模型调用写出短答复。资料里没有的扭矩、间隙、页码和参数不允许编造。

### 2.3 复杂问题交给下游的内容

Main 交给下游三样东西：完整原题、从现象和设备生成的评判注意事项、启动五路的标记。先前对话只作为现场约束附在原题后面，不把原题拆开。

## 3. 五个 SubAgent

五个 Sub 解的是同一道完整题。提示词相同，工具也相同，没有事先指定谁负责溯源、谁负责风险、谁负责写成工单。每一路按自己的理解决定查什么、先看什么、方案怎么写。编号只用来区分这五次独立求解。

每一轮先思考。思考时步数加一。然后：

- 步数达到上限：禁止再调用工具，用已有观察整理方案
- 模型给出最终方案：这一路结束
- 模型点名一个工具：执行工具，把观察送回下一轮

调试时每路默认最多 8 轮，程序硬上限是 50。每路还有 180 秒的总超时；剩余时间不足 8 秒时，不再请求模型，直接把已收集的观察整理成文字。某一路报错时，写成「方案生成失败」交给 Judge，其他路继续。五路请求会错开约 0.4 秒，减轻接口限流。

五路都可以使用 `search_mechanical`、`search_knowledge`、`lookup_baseline`、`lookup_grind_dialect`。用不用、先用哪一个，由该路自己决定。

## 4. 工具

工具都在本目录内，不读取旧项目的数据库。

| 工具 | 作用 | 谁可以使用 |
| --- | --- | --- |
| search_mechanical | 在 `knowledge` 目录检索维修短文。可带子系统过滤，例如主轴、砂轮、液压润滑 | 五路都可以 |
| search_knowledge | 与上一工具读同一批本地短文 | 五路都可以，简单题的 Main 也会用 |
| lookup_baseline | 读取测点模板：现场工具、常见原因方向、建议测点。不提供具体扭矩或间隙数值 | 五路都可以，简单题的 Main 也会用 |
| lookup_grind_dialect | 识别机床家族，并给出不要套用其他机型结构的维修约束。它不代替测量 | 五路都可以 |

`knowledge` 里目前有六篇短文：主轴发热与振动、砂轮平衡与振纹、静压轴承、头架与尾架、导轮与托板、冷却与表面烧伤。检索按标题和正文里的词打分，没有命中时明确说没查到，禁止把空白写成手册条款。

测点模板覆盖主轴、砂轮、头架尾架、导轮、液压润滑、冷却、进给、工作台。机床家族按原文识别 STUDER、高桥、MIKROSA、无心磨、内圆磨、平面磨和外圆磨。认不出家族时，方案只能给通用排查顺序。

## 5. Judge 评判标准

Judge 的输入是原题、Main 写的本题注意事项、五套方案。它只对每一套方案打 0 到 10 分，不另写一套维修步骤。加权总分由程序计算，不采用模型自己加出来的总分。

| 维度 | 权重 | 看什么 |
| --- | --- | --- |
| 故障定位准确性 | 30% | 是否对准用户描述的现象，有没有编造数值 |
| 操作安全性 | 25% | 有没有能量隔离、砂轮防护，有没有阻止带电带压拆卸 |
| 现场可行性 | 20% | 步骤能不能在机床旁边做，工具和测点是否具体 |
| 方案完整性 | 15% | 现象、排查、风险、验收是否都有 |
| 简洁性 | 10% | 是否把同一层排查写成长篇并列清单 |

总分等于五项分数乘对应权重后相加。生成失败的方案不参与评选。分数相同的时候，先比安全性，再比定位准确性。

Judge 还会为没有入选的方案写一句主要缺陷。最终页面先给出中选方案全文，再给评分表和这些缺陷。五路全部失败时，不假装有最优方案，只列出失败原因。评判模型本身调用失败时，仍会在已经写完的方案里做保底选择，并说明评分没有完成。

本题注意事项会写进评判提示，例如必须覆盖哪些现象、认出来的设备名称，以及用户提到的停机或量具限制。没有型号和实测时，注意事项要求方案只给排查顺序，不编造数值。

五项加权分用来选综合方案。它不代替下面的准确性专评。

## 5.1 准确性专评

五路方案完成后，准确性专评和 Judge 同时进行，互不改对方的分数。这个专评只回答两件事：哪一套准确性最高，这套的可信度是多少。

准确性看方案是否对准用户描述的现象，根因是否由这些现象推出来，有没有把用户没提到的故障写成已经确认的主因。

可信度看结论有多少能回溯到用户原文，或方案里写明的检查依据。没有出处的扭矩、间隙、压力、油压和精度数值会降分。没有实测时，写成待测和排查的可以给较高可信度；把猜测写成定论的要给低可信度。

两个分数都是 0 到 10。程序按准确性从高到低排序，准确性相同再比可信度。生成失败的方案不参加。专评调用失败时，加权评判仍然保留，页面会说明准确性专评没有完成。

如果加权最高和准确性最高不是同一套，两套都保留，并在结果里写明各自是谁。

## 6. 作者开关看到什么

诊断页的「作者开关」不改变链路，只决定页面额外显示哪些过程信息。

关闭时，页面只保留给用户的最终答复。

打开时，额外显示：

- 这是简单问题还是复杂问题
- 判断来自硬规则、分类模型，还是强制五路
- 一句判断理由
- 抽取出的现象、设备和约束
- 复杂问题时每一路的角色、状态、轮次、调用过的工具、方案原文
- 每一路的五项加权分数、加权分、是否加权中选
- 完整流程走向：Main 提取信息、复杂度分支、五路各自走到哪一步、Judge 和准确性专评、最后如何输出
- 每个 Sub 的思考过程：每一步的思考、调用的工具、工具参数和观察结果
- 准确性专评选出的那一路，以及它的准确性分数和可信度
- 每一路各自的准确性、可信度和一句理由

## 7. 现在的运行界限

每路默认 8 轮，是为了调试时控制消耗。确认稳定后，可以把页面上的「每路最多轮次」调到 50。50 是上限，不是建议的日常值。

本地资料是短篇排查笔记，不是机床说明书全文。方案里的具体压力、间隙和扭矩仍然必须来自现场测量或用户带来的本机资料，不能靠这六篇短文补全。
