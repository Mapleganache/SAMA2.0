## 案例数据库规范

本规范用于把机床维修、改造、控制、软件和 G 代码资料整理成可持续补充、可追溯、可查询的案例。原始资料不改写；数据库记录只做结构化索引和分析。

## 一、一个案例的固定结构

所有案例必须保留 `案例格式.txt` 的三段结构：

1. 基本信息：案例编号、机床品牌、型号、日期、控制系统、资料状态、验证状态。
2. 任务：机械故障、电路设计、电控设计、软件设计、G 代码设计。
3. 方法：机械故障处理、电路故障处理、新电路设计、电控设计、软件设计、G 代码设计。
4. 总的问题总结：当前是否可运行、已知风险、遗留问题、更优方案和回退条件。

没有资料的字段仍必须保留，内容写 `未提供`，数据库存储为 `NULL`，不得凭经验补造事实。

## 二、科学分类方法

目录分类与数据库分类分开：目录负责保存文件，数据库使用多维字段检索。

| 维度 | 推荐值 |
|---|---|
| 业务阶段 | 任务、诊断、设计、实施、验证、复盘 |
| 技术域 | 机械、电路、电控/PLC/PMC、CNC/NC、FP/HMI、G代码、伺服主轴、液压气动、通信网络 |
| 子系统 | 安全联锁、轴运动、手轮点动、主轴/砂轮、液压气动、冷却润滑、报警、辅助功能、文档注释 |
| 问题类型 | 逻辑错误、旁路风险、缺失联锁、地址/注释冲突、设计耦合、资料缺失、待现场核实 |
| 风险级别 | 高、中、低、注释质量 |
| 证据级别 | 原始程序、设备图纸、官方手册、导出说明、分析报告、现场测试 |
| 验证状态 | 未核实、桌面分析、待现场验证、现场已验证、已修复待复测、已关闭 |

一个问题可以同时属于多个技术域或子系统；不得只靠文件夹名称表达分类。

## 三、梯形图诊断强制规则

梯形图问题必须把地址和注释结合起来看，记录完整证据链：

`程序/网络 → 地址 → 当前注释或符号 → 指令与常开/常闭关系 → 上游来源 → 下游输出 → 电气图/现场实物 → 结论`

具体要求：

1. 地址是逻辑定位依据，注释是语义线索；两者必须同时入库。
2. 地址与注释冲突时，状态标为 `注释冲突`，结论标为 `待现场验证`，不得只按其中一个直接改程序或接线。
3. X/Y 实体 I/O 必须优先对照电气图、端子和现场器件；G/F 必须对照对应 CNC 接口手册；R/K/A/D 必须检查全部读写点和保持特性。
4. 必须记录网络号、程序段、源文件和行号；缺少任一项时保留空值。
5. 分清“程序中确实存在的逻辑”“依据注释作出的解释”“分析人员的推断”“现场已验证事实”。
6. 安全相关修改必须有备份、回退方案和验收步骤；桌面分析不得写成“已经修复”。

## 四、案例编号与文件名

案例编号：

`CASE-YYYYMMDD-品牌-型号-三位序号`

示例：`CASE-20260806-STUDER-S40-4-001`。

案例文件名：

`案例编号_主题.md`

问题编号保留原分析报告编号，同时在数据库中使用全局编号，例如：

`CASE-20260806-STUDER-S40-4-001:A-H01`

## 五、数据库分表原则

- `equipment`：设备主数据，一台机床型号只记录一次。
- `cases`：案例主表。
- `case_sections`：任务、方法和总结的固定字段；空字段仍保留。
- `issue_findings`：一个问题一行，不把多个故障塞进一个文本字段。
- `signals`：设备内的规范地址及主注释。
- `signal_comments`：同一地址在不同网络出现的注释，允许一址多注释并显式标冲突。
- `issue_signals`：问题与地址的多对多关系。
- `source_documents`、`case_sources`：来源和案例证据关系。

SQLite 文件、建库脚本和 SQL 结构位于 `00_知识库规范/案例数据库/`。

## 六、入库检查

每次新增或更新案例后至少检查：

1. 固定任务与方法字段是否齐全，缺失项是否明确为空。
2. 设备、型号、系统和日期是否有来源。
3. 梯形图结论是否同时关联地址和注释。
4. 是否把推断误写成现场事实。
5. 是否保留源文件路径、版本和验证状态。
6. 安全问题是否包含回退与验收要求。
