# SAMA 调参方法论

日期：2026-11-13  
适用：检索树、证据链、Agent、Judge 的参数与组件优化。

---

## 0. 结论先行

当前“全链路 + 20 题 + 大网格”的调参方式存在四个问题：

1. **慢**：一组 20 题要 30–40 分钟，12 组要 8 小时；
2. **噪声大**：20 题 ±2 题波动，5 vs 3 无法区分；
3. **多变量混杂**：一次改 6 个固定项，结果无法归因；
4. **目标错位**：只看总分，不看“哪题赢/哪题输”。

更好的办法是：

> **离线检索指标快速筛 → 小样本配对比较 → 50 题确认 → 最后才调生成层。**

---

## 1. 换目标：配对比较，不看裸总分

同一批题、同一判分模型，比较配置 A 与 B：

```
b = A 对、B 错的题数
c = A 错、B 对的题数
净胜 = b − c
```

判定标准：

| 净胜 | 结论 |
|---:|---|
| ≥ +3 | 有信号，可进入 50 题 |
| +1 ~ +2 | 噪声区，不算赢 |
| 0 | 无差异 |
| ≤ −1 | 放弃 |

统计工具：

- McNemar 检验（配对卡方）；
- 配对 bootstrap（重采样 1000 次，看净胜的 95% 区间是否跨 0）。

> 只看“原因 6/20 vs 9/20”会被题目难度稀释；配对比较只看“翻盘题”。

---

## 2. 分层调参（核心）

### 第 1 层：离线检索指标（不花 LLM token）

固定 50 题，只跑检索树，直接算：

| 指标 | 定义 |
|---|---|
| Gold Hit@K | 参考答案对应片段是否进 top-K |
| Recall@5 | 前 5 条覆盖的金标比例 |
| MRR | 第一个金标片段的倒数排名 |
| SUPPORT 率 | 有 SUPPORT 的题占比 |
| NEAR 率 | 只有 NEAR 的题占比 |

**几秒到几分钟一组**，可以扫：

```
topK ∈ {3,5,7}
hops ∈ {2,3,4}
γ ∈ {0.5,0.6,0.7,0.8}
λ ∈ {0.05,0.10,0.15,0.20}
beam ∈ {3,5,7}
budget ∈ {12,24,48}
minHops ∈ {0,1,2}
noNew ∈ {1,2,3}
```

先筛掉 80% 的坏组合，只把 Gold Hit 最高的 3 组送进第 2 层。

### 第 2 层：20 题端到端

只跑：

- 基线；
- 离线筛出的前 3 组。

做配对比较，净胜 ≥1 才进入下一层。

### 第 3 层：50 题确认

只对胜出的 1 组 + 基线跑 50 题：

- 净胜 ≥3；
- 置信区间不跨 0；
- 才允许上线。

### 第 4 层：生成层参数

`maxStep`、`pack M`、`Judge 阈值`、prompt 属于生成层，等检索层稳定后再动。

---

## 3. 单变量 + 坐标下降，不做全网格

从基线出发，每次只改一项：

```
基线
 ├─ topK 3→5
 ├─ hops 2→3
 ├─ λ 0.15→0.10
 ├─ γ 0.6→0.7
 ├─ beam 3→5
 ├─ maxStep 8→16
 ├─ noNew 1→2
 └─ minHops 0→1
```

只保留“净胜 ≥1”的项；再把保留项做 2×2 组合，验证是否叠加。

优点：

- 能归因；
- 成本低；
- 不会出现“六项一起改，掉分不知道谁干的”。

---

## 4. 分层抽样，别只看总分

把题按类型切开，每类至少 10 题：

| 类型 | 例子 |
|---|---|
| 报警号题 | 9177、908、417 |
| 案例题 | 例003、例040 |
| 磨床题 | 爬行、粗糙度、抱轴 |
| 非磨床题 | 刀塔、伺服、重装系统 |

某个参数可能只对一类有效，总分会被平均掉。

---

## 5. 先做组件消融，再调参数

参数之前先确认组件：

```
基线
 ├─ +D_pack
 ├─ +expand_tree
 ├─ +证据 Judge
 └─ +元素入口
```

每项单独开关，20 题配对。

> 如果组件本身是负收益，调它的参数没有意义。  
> 这是前面几轮最大的教训。

---

## 6. 实验纪律

1. **同一库、同一题、同一判分模型**；
2. Judge 温度 0，失败重试，禁止用失败样本充数；
3. 记录配置哈希 + 每题结果，便于复算；
4. 一次只改一个变量；
5. 设停止规则：

```
连续 3 组都打不过基线 → 停止该方向，保留基线。
```

6. 任何改动先跑 5 题冒烟，确认流程正常，再跑 20 题。

---

## 7. 建议的执行顺序

```
0. 基线复现（20 题）
1. 离线检索扫描：topK/hops/γ/λ/beam/budget（不花 LLM）
2. 取前 3 + 基线，20 题配对
3. 胜者跑 50 题，净胜 ≥3 才保留
4. 再单独试 maxStep / pack M / Judge 阈值
5. 最后做组件消融，确认每个部件都有正收益
```

---

## 8. 具体到 SAMA 的落地方案

### 8.1 先建离线扫描脚本

输入：

- 题库：`eval50`（50 题，含金标片段/案例 id）；
- 库：`sama_v2_holdout50.sqlite`；
- 参数：一组配置。

输出：

```json
{
  "config": {"topK":5,"hops":3,"gamma":0.7,"lambda":0.1,"beam":3,"budget":24},
  "goldHit": 0.42,
  "recall5": 0.31,
  "mrr": 0.22,
  "supportRate": 0.55
}
```

只调用 `runRetrievalTree`，不调用 LLM。

### 8.2 扫描策略

- 第一阶段：单变量，8 组；
- 第二阶段：保留项 2×2，最多 6 组；
- 全部离线完成，预计 **20–30 分钟**。

### 8.3 端到端确认

离线前 3 组 + 基线：

- 20 题配对；
- 只对净胜 ≥1 的组跑 50 题；
- 50 题净胜 ≥3 才上线。

---

## 9. 指标与判定表

| 阶段 | 样本 | 指标 | 通过条件 |
|---|---|---:|---|
| 离线扫描 | 50 | Gold Hit / Recall@5 | 进入前 3 |
| 小样本 | 20 | 配对净胜 | ≥ +1 |
| 确认 | 50 | 配对净胜 + CI | ≥ +3 且 CI 不跨 0 |
| 回归 | 50 库内 | 原因/处置 | 不低于基线 |

---

## 10. 一句话

> **调参不是“找最高分”，是“用最小成本排除坏假设”。**  
> 先用离线检索指标快速筛，再用配对比较确认，最后才花 LLM 跑 50 题。
