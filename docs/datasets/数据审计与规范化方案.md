## 二、根因

1. **统一按“散文”切**：`清洗→按标题切 500-800 字`，没有区分目录、表格、列表；
2. **标题识别太宽**：`^\d+(\.\d+)*\s+\S` 会把“2015 年 4 月…”当标题；
3. **PDF 表格没有解析**：只取文本流，行列关系丢失；
4. **DOCX 表格只拼了 ` | `**，没有保留列名和行；
5. **没有实体层**：报警号、参数号、案例没有结构，检索只能按字面碰；
6. **没有质量门**：切完直接入库，坏片段也进索引。

---

## 三、规范化 v2

### 3.1 文档层

- **目录页识别**：连续 ≥3 行含 `…{2,}` / `.{4,}` / `例\d+` → 整块标 `toc`，不入检索；
- **页眉页脚**：跨页重复行（数字归一化后计数）→ 丢弃；
- **标题识别**（按优先级）：
  1. `第X章/节/篇`、`模块X`、`例\d+`、`附录X`、`一、二、`
  2. `1.2.3 标题`（层级 ≤ 4，长度 ≤ 28，不以句号结尾）
  3. PDF 有字体信息时，用字号/加粗判定标题（pymupdf `get_text("dict")`）
- **章节路径**：`文件 / 章 / 节 / 小节`，作为 `hierarchy`。

### 3.2 块模型（替代“直接切片”）

新增 `doc_blocks`：

```
doc_blocks(
  id, file_id, page_start, page_end,
  block_type,        -- heading | para | table | list | figure_caption | toc | furniture
  section_path,      -- 章/节/小节
  text,              -- 纯文本
  cells_json,        -- 表格：[[...],[...]]
  bbox,              -- 可选：坐标
  order_no
)
```

片段只从 `para/list` 生成；`table` 走实体抽取；`toc/furniture` 直接丢弃。

### 3.3 表格解析

| 来源 | 方法 |
|---|---|
| DOCX | `python-docx` 读真实表格（列名、行） |
| PDF 文本层 | `pymupdf` 的 `page.find_tables()` |
| OCR | 文字框坐标按 y 聚类成行、x 切列 |
| Excel | 直接读行列 |

表格先落 `cells_json`，再按表头映射到实体：

```
alarm_codes(code, controller, meaning, cause, action, source)
parameters(param_no, name, unit, default, note, source)
cases(symptom, cause, action, machine, source)
```

### 3.4 检索层（关键）

1. **实体精确查表优先**：识别问题里的报警号/参数号（`#411`、`ALM411`、`Pr961`、`参数1221`），先查 `alarm_codes` / `parameters`；
2. **代码规范化**：`#411 / 411 / ALM411 / ALM 411` → `411`，原文保留展示；
3. **块级 BM25**：标题、章节路径、正文分字段加权；`block_type=table` 的文本带列名；
4. **引用格式**：`文件 / 章节 / 页码 / 表行`，不再出现“25 例”；
5. **回退**：实体没命中再走文本检索，并在回答里说明“未查到该报警号的表项”。

### 3.5 质量门（每文件必过）

| 指标 | 阈值 | 处理 |
|---|---|---|
| 目录块占比 | > 10% | 重新切分或标记 |
| 标题与章节不符 | > 5% | 降级为“书名/页码”并告警 |
| 表格解析率 | < 80% | 该文件表格不进实体层 |
| OCR 乱码率 | > 15% | 标 `ocr_unverified`，不放开 |
| 繁体残留 | > 1% | 重新转换 |
| 与现有库重复 | > 0 | 去重后再入库 |

不达标的文件 **不入检索**，只在 `manifest` 里记录原因。

## 五、试点结果（2026-11-07）

| FANUC 案例 | **523 条**（521 条有故障现象，含检查分析、故障处理） |
| 旧碎片替换 | FANUC 500 例 408 条乱切片段、新代报警 23 条表格片段全部替换 |
| 新工具 | `lookup_alarm(code)` 精确查表 |
| 门控调整 | 带「例NNN / #411 / ALM411」的问题不再被“缺机型/工况”追问 |

验证：

- `OP-001` 问句：回答直接来自报警表（轴板设定错误、参数 No.1、BIOS IRQ11、轴卡指拨开关、替换轴卡），正确；
- `例001` 问句：不再返回 need_info，进入方案生成并引用案例片段；
- `#411` 问句：直接 SQL 检索能命中 `CASE-328/329`（显示器出现#411报警），但该次生成未采用，仍需在提示/选路层强制优先 case_entry。

结论：**结构化后的报警表可用；案例条目能被检索，但模型没有稳定采用**，这是下一轮要修的点。

## 六、40 题正式评测（2026-11-07）

题目：20 道新代报警号题 + 20 道 FANUC 现象案例题（不含案例号，测现象匹配）；走前端 `/api/ask`，主选/备选分别对照参考答案判分。

| 分组 | 主选原因/含义 | 主选处置 | 备选原因 | 备选处置 | 任一命中（原因/处置） |
|---|---|---|---|---|---|
| 报警号 20 题 | **19 / 20（95%）** | 14 / 20（70%） | —（简单题只出一份） | — | 19 / 14 |
| 现象案例 20 题 | **17 / 20（85%）** | 16 / 20（80%） | 15 / 20 | 15 / 20 | 18 / 17 |

说明：

- 报警题走 simple 路由，只交付一份答案，因此没有备选；
- 处置命中率低于原因，是因为部分报警条目原文只给“原因”，没有独立的“排除方法”；
- 现象题没有案例号，靠 `cases.symptom` 匹配到案例条目后作答，主选 85% 命中；
- 1 道题（例364）返回 `no_plan`。

结论：**结构化查表把“库里有数据但答不准”的核心问题解决了**；剩余短板是报警表的“排除方法”字段缺失率，以及少量案例未被匹配。
