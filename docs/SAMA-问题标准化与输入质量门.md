# SAMA 问题标准化与输入质量门（设计记录，待实现）

日期：2026-11-07
状态：**只记录设计，本轮不实现**
背景：评测用的题目都是“标准问法”（有机型、有现象、有工况、指向明确），真实用户不会这样问。需要一层“问题标准化 + 输入质量判断”，在进入诊断流程前把用户输入变成可诊断的形式，并区分“能答 / 要澄清 / 超范围”。

---

## 一、真实用户输入会长什么样

| 类型 | 例子 | 问题 |
|---|---|---|
| 口语化 | “床子响得厉害，咋整” | “床子”=机床，“响”=异响，缺机型/工况 |
| 错别字/别称 | “磨头抱死”“主轴咬死”“导轨爬行” | 术语不统一 |
| 只有报警号 | “401 报警” | 缺机型、缺现象 |
| 现象+多问题 | “主轴发热还振动，是轴承问题吗？要换吗？多少钱？” | 一次多问，需拆解 |
| 粘贴表格/手册 | 整段 OCR 文本 | 不是问题，需先提炼 |
| 繁体/英文混写 | “主軸轉速不穩”、“ALM 930” | 需繁简/术语归一 |
| 无现象只有结论 | “磨床坏了” | 无法定位 |
| 超范围 | “帮我写个 G 代码”“CNC 报价多少” | 不属于故障诊断 |

## 二、目标

在 `intake` 之后、分类/门控之前，增加一层：

```
用户输入 → 输入质量判断 → 标准化 → 决策（直接答 / 追问 / 超范围）
```

输出统一结构：

```json
{
  "intent": "fault_diagnosis | alarm_lookup | parameter_lookup | howto | out_of_scope",
  "quality": 0.0,
  "normalized_query": "数控磨床，热机，主轴异响，空载时有轻微响声",
  "extracted": {
    "machine": "数控磨床",
    "controller": "FANUC",
    "phenomena": ["异响"],
    "alarm_code": "",
    "load": "空载",
    "thermal": "热机"
  },
  "missing": ["machine_model"],
  "needs_clarify": false,
  "clarify_questions": [],
  "notes": "把“床子”归一为机床；“响”归一为异响"
}
```

## 三、两层实现

### 3.1 规则层（零成本，先做）

- 长度 < 6 或 > 800 → 标记异常；
- 是否包含：机型词、现象词（复用 `gaps.PHENOMENA`）、报警号（`#\d{3,4}`、`ALM\d+`、`OP-\d+`）、工况词（空载/磨削/热机/冷机）；
- 多问句检测：`？` 数量、并列“吗/呢/多少/怎么收费”；
- 粘贴检测：连续多行、表格符号 `|`、与问题无关的目录行；
- 繁简检测：繁体字比例 > 20% → 先转简体；
- 超范围关键词：报价、招聘、写代码、翻译、天气等。

规则层只做“标记 + 提示”，不直接改写。

### 3.2 模型层（同模型、低温度、强约束）

输入：用户原话 + 规则层标记 + 当前设备的已知上下文。
输出：上面的 JSON。

约束：

1. **只做同义归一**（床子→机床、咬死→抱死、响→异响），**不得补充用户没说的机型、工况、测量值**；
2. 补充的内容必须进 `assumptions`，不能写进 `extracted`；
3. 多问句必须拆成主问题 + 次要问题，主问题只保留一个；
4. 置信度 < 0.6 或 intent 不明确 → `needs_clarify = true`，给出 1–2 个澄清问题；
5. 超范围直接返回 `out_of_scope`，并说明能力边界。

## 四、决策规则

| 条件 | 动作 |
|---|---|
| `intent = out_of_scope` | 告知能力边界，不进入诊断 |
| 有报警号/案例号 | 走确定性查表（`lookupStructured`），必要时补 1 个澄清问题 |
| 有现象 + 有机型（或型号未知但可假设） | 直接进入现有分类/采样流程，假设写入 `assumptions` |
| 有现象、缺工况 | 按现有软门控：先给方案 + 待确认问题 |
| 无现象、无报警号、无机型 | 追问（沿用现有硬门控），但问题要具体 |
| 粘贴大段文本 | 先提炼成一句现象描述，请用户确认 |

## 五、与现有代码的关系

- 现有 `gaps.gateDecision` 已经处理“缺机型/现象/工况”；
- 新层放在它**前面**，产出 `normalizedQuery` 与 `quality`，再交给现有门控；
- 不替换现有规则，避免一次性大改；
- 新增开关 `SAMA2_INPUT_NORMALIZE=1`，可灰度。

## 六、评测方案

构造 100 条“不规范输入”：

- 口语 30 条（床子响、磨头咬死、工件烧伤）；
- 只有报警号 20 条（401、ALM930、OP-001）；
- 错别字/别称 20 条（抱轴→抱死、爬行→爬动）；
- 多问句 15 条；
- 粘贴/目录 10 条；
- 超范围 5 条。

指标：

| 指标 | 目标 |
|---|---|
| 标准化正确率（人工抽检） | ≥ 90% |
| 误改率（改变用户原意） | ≤ 2% |
| 该追问时追问的比例 | ≥ 90% |
| 不该追问时误追问 | ≤ 5% |
| 端到端答案正确率（对比未标准化） | 提升 ≥ 10 个百分点 |

## 七、风险

1. **过度改写**：模型可能把“不确定”改成“确定”，必须限制只做同义替换；
2. **补造信息**：绝不能把推测的机型/工况写成已知；
3. **延迟**：多一次模型调用，简单题从 ~2s 增到 ~4s，可接受；可用小模型；
4. **多语言/繁体**：先转换再判断，避免术语对不上。

## 八、落地顺序（后续实现）

1. 规则层 + 日志采集（记录真实用户输入与门控结果，先看分布）；
